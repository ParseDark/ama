System field guide · AMA Memory

不只是记住。
而是有依据地想起。

从一次对话，到长期偏好、可查资料与任务经验。AMA 的记忆系统负责决定：什么值得留下、何时应该出现，以及什么时候需要改变。

来源可追溯按需召回后台核验用户可控
记忆是可修正的判断，
不是永久正确的事实。

本文区分当前实现与未来方向。基于 memory 优化提交 a7b9eb9；交互内容仅作流程说明，不连接你的真实记忆或任何服务。

01 / Big picture

一个有证据底座的闭环

原始对话留下证据；结构化记忆保存提炼后的判断。在线路径解决“现在用什么”，后台路径解决“以后还对不对”。

CAPTURE → ORGANIZE → RECALL → REVIEW历史经验 ≠ 当前事实 ≠ 新授权
INPUT A / 自动学习对话中的用户信号

以用户原话为证据；审批与停止仅作辅助。过滤隐私会话与敏感站点，分批提炼、去重，再形成习惯候选。

INPUT B / 明确保存“请记住这个偏好 / 资料 / 流程”

通过 remember 工具保存。按意图、内容和类别决定确认要求，保留全局或当前站点的作用域。

↙ 两条使用与维护路径 ↘

在线：为当前任务找回必要内容

当前消息与站点 → 过滤适用记忆 → 相关性检索 → 有界上下文注入或按需读取。

偏好指导回答；资料和流程只是历史参考。

后台：依据原始证据重新检查

有来源的偏好 → 读取原始用户证据与近期信号 → 保留 / 建议修订 / 建议停用。

修订与停用建议必须由用户接受。

底座：本地对话与记忆存储 + 可回查来源 + 可选的现有 embedding endpoint / 向量缓存

02 / Three kinds of memory

不同的记忆，不同的出场方式

不是所有保存内容都应该变成每次回答必须遵守的规则。

01 · PREFERENCE

偏好

回答“你希望我怎么做”。适用且有效的偏好优先进入有限的上下文；当前用户要求可以覆盖旧偏好。

示例 · 全局偏好“默认用中文，先给结论，再给细节。”
02 · REFERENCE

资料

回答“你保存过什么”。相关时召回，或通过 recall_memory 主动读取；不自动升级为行为指令。

示例 · 站点资料“这个项目的发布检查清单在文档目录里。”
03 · PROCEDURE

任务流程

回答“类似任务以前怎么完成”。目前由用户明确要求保存，复用资料检索路径，不作为常驻偏好注入。

示例 · 需再次验证“导出报表前，先核对日期与筛选条件，再选择 CSV。”
当前边界：流程记忆仍是一条简短的参考文本，不是自动生成的技能库、可执行脚本或保证成功的任务模板。普通模式下保存流程需要确认；私密或敏感站点会话不允许保存流程。
03 / Follow a memory

一条记忆如何被学会、找回与修正

选择一个场景查看完整路径。以下是静态讲解，不会保存、发送或修改真实数据。

SCENARIO A · 正常模式下的自动学习

“以后回答先给结论。”
  1. 读取用户证据

    提取原始用户消息，绑定会话、消息 ID 与内容哈希。助手文字和网页内容不能证明用户偏好。

  2. 形成习惯候选

    模型必须引用实际提供的 source ID。去重并累计独立用户消息；同一消息重放不增加证据。

  3. 等待用户确认

    通常达到两条独立用户消息的证据门槛后，形成建议。用户可确认，也可拒绝或直接手动保存。

  4. 在适用时使用

    确认后成为可用偏好，按作用域和预算选择。用户这次说“只给详细推导”时，以当前要求为准。

Danger mode 的区别：达到证据门槛的自动习惯可直接激活，不等待建议确认。但隐私过滤仍保留；后台核验的修订与停用仍须用户接受。

SCENARIO B · 用户已经明确保存过流程

“按上次的方法帮我准备报表导出。”
  1. 定位相关经验

    过滤失效、禁用及不适用站点的记忆。有可用向量时做语义匹配，失败则降级处理。

  2. 按需展开内容

    相关流程可进入预算内的参考块；未注入的资料通过 recall_memory 读取，而不是全部塞进 prompt。

  3. 必要时回看来源

    read_history_source 按会话与用户消息定位原始回合，分页读取文字，不重放历史工具操作。

  4. 重新核对并授权

    核对当前页面、字段与目标。旧步骤不保证页面仍相同，过去批准过导出也不等于这次已批准。

没有 embedding 也不是“没有记忆”：偏好仍可使用，资料通过有界目录与关键词召回降级。检索失败不应伪装成已找到相关证据。

SCENARIO C · 通过后台核验发现偏好可能变化

“之前要简短，现在默认给完整解释。”
  1. 独立安排核验

    即使没有新学习信号，也能在后台触发维护；学习尚有待处理批次时，先完成学习再核验。

  2. 检查原始依据

    对照原始用户来源和近期消息。原始消息缺失、被删除或无法安全读取，都不等于旧偏好为假。

  3. 提出可解释建议

    明确矛盾才能建议 revise 或 archive，并引用提供的用户证据。没有新提及不构成停用理由。

  4. 保留原文等确认

    用户可接受修改或保留当前内容。后台不会偷偷重写，即使这条记忆被置顶或开启 Danger mode。

这个场景说明后台核验路径；明确的 remember 或用户手动编辑也可以更新记忆，不必等待每日维护。当前核验仅覆盖有来源的偏好，不核验资料与流程内容的正确性。
04 / Evidence, not just text

每条记忆，带着“为什么”

内容之外的元数据，决定它能否被解释、纠正和安全使用。

一条记忆的结构 · 示意

text
“默认先给结论”
category
preference / reference / procedure
scope
global 或 domain:example.com
sources
来源 ID、会话 ID、消息 ID、信号类型、内容哈希与可选站点
verification
inferred 或 user-confirmed
review
待确认的修订 / 停用建议、理由与证据
changes
最近 20 条变更记录，而非无限审计日志

这些字段解决什么问题？

  • 追溯：从记忆回到产生判断的用户原话，而不是只相信模型写的摘要。
  • 防止证据膨胀：同一消息不能因重复处理或多次改写被计为多个独立证据。
  • 区分推断与确认：用户确认说明用户接受了内容，不代表系统完成了外部事实认证。
  • 可逆维护：建议先挂在记忆上，原文不变；接受后再修改或停用。
  • 兼容旧记忆：来源字段可选。旧数据不伪造出处，也不会为补来源自动重放已消费的历史。
来源 ID 与哈希用于关联和检查原始内容，不是密码学签名或防篡改证明。模型引用真实 source ID，也仍可能误读其含义。
05 / Bounded by design

控制上下文，也控制维护成本

这些是当前实现的处理上限与冷却策略，不是模型准确率或执行时间承诺。

450token 估算预算
包含最终偏好块、引用目录与召回提示
60常规学习批次信号上限
同一消息组与同时间事件原子处理，可能略超
5每轮最多核验的偏好数

学习游标只推进到已消费的位置；未处理批次会安排继续，不先跳过再截断。Token 使用 estimateTokens() 估算，并非供应商 tokenizer 的硬保证。原始历史读取每页最多 6,000 字符；核验近期信号最多覆盖 10 个会话、60 条用户消息。

Embedding 是查找基础设施

复用当前配置的 endpoint 和向量缓存，可使用本地 Jina 服务。用于资料 / 流程召回、语义历史搜索、去重候选与核验优先级；它不是记忆数据库，也不负责判断真假。

可选、默认关闭、可降级

关闭、离线或忙碌时，不阻断基本记忆功能。关联判断采用有界候选降级，维护保留按核验时间排序；查询与缓存填充避免自相竞争，但服务超时仍可能发生。

06 / Trust & privacy

本地存储，不等于从不离开设备

记忆属于用户。存储、模型处理与执行授权是三件不同的事。

边界 当前行为 不要误解为
存储与同步 记忆、历史、向量留在本地扩展存储；不随可选配置同步上传。配置同步本身可包含凭证。 本地不代表加密，也不是密码保险箱。
模型与向量服务 学习 / 核验所需证据和召回内容可发给配置的聊天模型；语义功能会将相关文本发给配置的 embedding endpoint。 默认使用本地 Jina 的示例，不代表所有用户都只走本机。
自动学习 排除隐私会话、敏感站点信号；不能从助手、页面或工具输出建立偏好；批准 / 停止单独不足以证明习惯。 自动学习不是完整浏览记录抓取。
明确保存 一般敏感内容经必要确认后可保存为按需资料；流程在私密或敏感站点上下文中被拒绝。 自动学习的排除规则，不等于禁止用户明确保存所有敏感资料。
原始来源 read_history_source 需要真实会话与用户消息，拒绝隐私回合，分页返回历史文本。其过滤不等同于自动学习的敏感域名过滤。 不能据此声称所有敏感站点的历史都不可读取。
执行授权 历史文字按不可信数据处理；流程先验证当前页面与条件，写入等操作继续遵守当前审批模式。 过去点过“允许”，不代表永久允许。
07 / Where next

先证明有用，再扩大记忆

下面只有第一阶段已有基础实现；其余是建议演进方向，不是已交付功能或排期承诺。

  1. 01 / 已建立基础

    证据与控制

    来源追踪、独立证据计数、原始对话回查、核验建议与用户确认。先回答“为什么记住”。

  2. 02 / 建议下一步

    评测与可观测性

    建立召回、误用、纠错与隐私评测；解释每次用了哪些记忆、为何选中、是否降级。回答“到底有没有帮助”。

  3. 03 / 后续方向

    经验证的任务经验

    记录适用条件、可观察成功结果、失败恢复与最近验证时间。自动提炼先生成候选，不把助手说“完成”当成成功证据。

  4. 04 / 按规模决定

    项目知识网络

    当资料和经验足够丰富，再增加项目索引、主题关系和摘要。不是现在就把所有内容堆成一座 Wiki。

08 / Read the fine print

几个容易混淆的问题

这次验证能证明什么，不能证明什么？

memory 优化提交已通过 260 项单元 / 集成测试、34 项扩展 E2E、独立的真实本地 Jina 集成测试，以及类型、格式和生产构建检查。E2E 使用模拟 LLM，本地向量测试使用合成文本；它们证明特定路径可运行，不证明线上召回准确率、真实模型核验质量或精确 token 上限。本文新增的 HTML 不改变 memory 运行逻辑。

后台“保留”是否意味着这条记忆已被验证为真？

不是。“保留”只是模型对提供证据做了一次检查。当前确认状态只有 inferred 与 user-confirmed，没有独立的“事实已认证”状态。缺少来源的旧记忆不会被自动补成有证据的记忆；来源丢失也不等于内容错误。

Memory 和聊天 Compact 有什么区别？

Compact 是为当前会话压缩较早上下文的有损摘要，原始对话仍保留。Memory 是跨对话可复用、带作用域和生命周期的内容。两者都不能提供新的授权，也不应替代对当前页面状态的读取。

想深入代码，从哪里开始？

从 learning 看入口，从 signals / extractor / merger 看证据如何进入，从 selector / retrieval 看内容如何被选中，再读 maintenance 与 store 看如何维护。页面链接适合在本地仓库中打开；GitHub 的普通文件页只展示 HTML 源码，需下载后在浏览器打开。
