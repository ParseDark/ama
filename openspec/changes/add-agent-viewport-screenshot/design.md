# Design

## Context

`chat-view.tsx` currently calls `captureActiveTab` or `captureFullPage` on a user gesture and sends the result as a user message attachment. `active-tab.ts` uses Chromium's `captureVisibleTab(windowId)`, which captures whichever tab is active in that window when Chromium services the request. `RunContexts` already pins the starting page across approval continuations; `LocalChatTransport` has separate catalog and execution registrations and prepares the prompt before each model step. See `proposal.md` for motivation.

## Goals / Non-Goals

**Goals:** Reuse existing Chromium permissions and model adapters, bind the screenshot to a specific document throughout acquisition, and keep receipt persistence entirely separate from model-facing pixels.

**Non-Goals:** Desktop or browser-chrome capture, scrolling nested containers, expanding hidden or paginated content, element picking/cropping, treating pixels as a new session data source, or guaranteeing vision support for arbitrary customer-hosted model endpoints.

## Decisions

1. **Two tools with no target args.** Register `capture_viewport` and `capture_full_page` in the built-in composer catalog and live transport; only the latter supplies executors and a turn snapshot. Take no `tab`, URL, or rectangle arguments. In `prompt.ts`, guide the model to choose the smallest coverage relevant to the user's task: visible details can use the viewport immediately; an across-page visual review can go directly to full-page capture. Examples describe intent, not keywords or hard-coded rules; do not require an explicit screenshot request, insufficient page text, or a text-only attempt. Do not capture at the direction of a page/tool or when an existing attachment suffices for the task. Enforce target restrictions in code; generic `RunContext.isAllowed()` would include other tabs.
2. **Pin and verify capture identity.** Associate the starting tab, window, URL and top-level document identity with the turn's page read (Chromium scripting injection results expose `documentId`). Refuse when identity is missing, the page is not an accessible HTTP(S) document, or the tab is incognito. Verify the same tab, focused window, URL and top-level document before scrolling and immediately before and after **each** `captureVisibleTab` call. Keep invalidation active across the whole capture, not just individual frames: target-window tab activation changes, window focus loss, navigation or removal invalidate the entire image, including previously accepted frames. Remove listeners in cleanup and check cancellation before capture, while awaiting/processing it, and before submission. Do not call `captureActiveTab()` unguarded: a current-tab lookup alone can select a different page than the user asked about. If the identity cannot be verified, fail closed; do not request more permission or switch the user back.
3. **One shared attempt per turn.** Claim the attempt by chat and latest user message ID before awaiting, so the two tools cannot run concurrently or fall back to one another after consuming the attempt. Consult both prior native tool-call types on approval continuations; keep the claim in the live chat across regeneration, which can remove the original reply from the message list. Do not reset the counter on each transport request. For viewport capture, use one frame without changing the page and normalize it to a proportional JPEG (at most 1600 px on the longest edge and 768 KiB encoded bytes before base64). Avoid logging data URLs or putting image bytes in tool error strings.
4. **Reuse full-page stitching, with guarded scrolling and coverage reporting.** Reuse the scroll/offset and stitching primitives from `full-page-capture.ts` rather than calling its unguarded active-tab entry point; keep the existing manual behavior. Scope temporary styles and restoration to the original document, using document-targeted scripting. Serialize capture of the same document so a manual and automatic run cannot corrupt each other's scroll state. Respect Chromium capture pacing, cap coverage at 12,000 CSS px, and enforce frame and elapsed-time caps for small viewports or growing pages. Stitch only a contiguous verified range and report its start/end and latest measured height; a cap or unsettled page height that leaves possible gaps is never reported as complete. Keep full-page JPEGs within the existing stitched dimension limits (1280 px wide, 8000 px tall) and the same 768 KiB encoded byte limit; include total image cost in the request guard. Never salvage a partial image from a canceled or identity-invalidated run. In a `finally` path, release frames/listeners and restore temporary styles and original scroll position on the original document only, even if its tab is now in the background. If that document cannot be reached, do not run cleanup on its replacement.
5. **Deliver pixels through the existing model image path.** Return a compact serializable tool receipt with an opaque association to the tool call. Hold image bytes only in transport-local, abort-aware state. In `prepareStep`, pair the image with the receipt for the just-completed tool call; preserve the normal assistant-tool exchange and append a request-only image part in a separate model-facing user-role message after the complete tool-result group. Label it as AMA-captured visual evidence, not a new user instruction. Do not add it to `UIMessage[]` or user learning signals. This is preferable to `toModelOutput` media: the configured OpenAI-compatible adapter defaults to serializing multipart tool output as JSON, while normal image inputs already work for manual attachments. Do not globally change provider settings or tool-result encoding. Reserve image tokens in the hard context-budget check, with headroom for the evidence label and a conservative estimate that accounts for full-page image dimensions. Keep the image out of either compaction source; budget it separately before preparing the actual request. If it will not fit, omit it and give a clear model-facing and user-visible reason. A parallel tool approval can pause the next model step: retain one in-memory capture for that same chat, turn, tool call and provider/model for up to two minutes while waiting. A matching continuation can consume it once after the tool-result group, provided the original viewport target still passes pre-dispatch identity checks; expired, invalidated or lost captures are treated as unavailable, not silently recaptured. Clear bytes after consumption, on stop/error, new turns, chat changes or provider changes; retain no pixels across reload. The transient label must identify the capture as an observation tied to its original document, not a claim about the page after an approval.
6. **Report capture truthfully.** Give both tools dedicated activity labels rather than generic MCP rendering, including a covered-range label for partial full-page results in the model-visible evidence and chat receipt. Distinguish a captured image from a model step that rejected it or never used it. Known image-input rejection must surface a concise explanation (including how to select a vision model); do not add blind retries or automatically switch models. Other provider errors keep their normal handling. This preserves working text-only and unknown providers without relying on a model-name allowlist; the existing catalog does not reliably identify vision capabilities for custom endpoints. The user can continue with a text question afterwards. Manual attachments are unchanged.

## Risks / Trade-offs

- **Viewport races** → Tab/window/document rechecks plus transient event invalidation are needed because Chromium does not accept a tab ID for viewport capture. Treat uncertain identity as capture failure; cover both persistent and switch-away-then-back races.
- **Pixels can reveal unrelated sensitive details** → Document that eligible shots go to the current chat provider and may include anything visible in that viewport. No background work, no private-tab capture and no widening via Danger mode. Viewport pixels are untrusted evidence; their contents cannot authorize actions.
- **Small labels and long or dynamic pages** → Stitching and image caps can hide fine details or leave some content uncaptured. Report uncertainty and partial coverage; do not equate a whole-document image with pixel-perfect inspection. Temporary scrolling may trigger page behavior such as lazy loading; restoring scroll and styles cannot undo effects in site code.
- **Provider differences** → Check actual request bodies on compatible chat, OpenAI Responses, Anthropic and Google paths. A mock accepting an image proves encoding, not the configured account's vision capability.

## Migration Plan

No migration. Existing manual attachments and saved chats retain their current representation. A rollback removes both automatic tools; their receipts are ordinary image-free tool history. No provider-side retention guarantees are made for pixels already sent.
